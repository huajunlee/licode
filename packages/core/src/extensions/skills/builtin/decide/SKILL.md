# 帮用户做决定

用户把一个决定交给你，他要的不是标准答案，是**在他自己历史与处境上**做出来的判断。泛泛的建议（"看你的职业规划""权衡利弊"）对他没有价值——那种话他自己也会说。

所以这套流程的核心是**取证**：先把用户过去说过、做过、在意过的东西找出来，再在上面给分析。证据不够时坦诚讲出来，而不是编一个听起来合理的答案——那比不给建议更糟，因为它看起来可信，用户会当真。

## 什么时候不该用

用户要的是**取向**时才用。"我该不该换工作""这两个 offer 选哪个""要不要跟爸妈说"，这是在要取向。

下面这些不是：闲聊、问事实（"我上次说什么时候去报到"）、让你执行任务（"帮我写封邮件"）。

还有一类容易误判的：**技术选型、代码方案**这种没有个人历史可依据的选择。它该直接答——没有日记和人物档案可查，套上这套流程只会找不到着力点，反而绕远。这套流程处理的是**个人处境**里的取舍。

硬套只会把简单的事变啰嗦。

## 第一步：取证

**先看你手上已有的。** 用户当下这句话本身就是证据——他描述处境时说的原因、顾虑、提到的人和事，都是现成的。别只顾着往下搜，把用户刚说的话晾在一边。日记是空的（新用户很正常）时这一点尤其重要：这时 B 式本就无从谈起，把用户当场说的当作依据，该降 C 就降 C，别硬撑也别编。

再去看两处。（另外，系统已把**长期记忆**自动注入上下文——那部分不用你去搜，但要在判断里用上。）

**历史与事实** —— 用 `journal_recall` 工具。它按关键词、人名或日期范围搜日记，返回相关的历史决定、事实与事件。

搜索词要选准：**用能定位这件事的词，而不是宽泛的词**。"换工作"比"工作"好，"和爸妈的关系"比"关系"好。没搜到就换个词再试一两次；确实没有就如实说"没找到相关记录"，别顺着话往下编。

**人物** —— 档案在 `.licode/people/`，一人一个 markdown 文件。文件名是规范化后的人名（如 `爸妈.md`），内容分三块：

- frontmatter：`canonicalName`（正式名）、`aliases`（别名）、`lastSeen`、`summary`
- `## 概述`：一段概括
- `## 结构化`：JSON，含 `traits`（特质）、`preferences`（喜好）、`interactions`（互动）、`relationshipState`（关系变化）

决策涉及具体的人时（用户提到某人，或历史里反复出现某人）就去读档案。**别名可能和文件名对不上**，所以先用 Glob 看看目录里都有谁，必要时按 `aliases` 里的名字 Grep 找。

读档案比凭印象推断人物立场可靠得多——用户一眼就能看出你在猜。目录不存在、或没有相关的人，正常说明即可。

## 第二步：判断简单还是复杂

**简单**：二选一、stakes 低、当前上下文够用、用户想快点拿到意见 —— 取证后直接给分析。

**复杂**：命中下面任一条，就先规划再动手：

- 多维度权衡（两个以上互相竞争的维度）
- 高 stakes、难撤销（职业、大额支出、重大关系）
- 信息不足，需要跨多个主题或人物定向召回
- 选项三个以上
- 影响周期长（以月、年计）

## 复杂路径：先规划，再评审，再执行

复杂决策一次性给答案容易走偏——漏维度、选项太窄、召回没方向。先把计划**写出来**，写出来它就成了看得见、可被检查的东西：

**1. 写计划**，包含：

- **决策问题**：完整处境描述，不是几个词
- **维度**：要权衡的方面 + 每个方面的具体评估目标。写"成长：未来 3 年技术成长空间"，不要只写"成长"
- **选项**：至少两条真正可行的路径
- **相关人物**：涉及的人 + 与用户的关系
- **执行步骤**：每步说明要召回或收集什么

**2. 把计划交给 `decide_reflect` 评审。** 这一步的价值在于**换一个模型、且只看到计划本身**来挑毛病——你自己评自己，会锚定在已经想好的东西上。它返回 `passed: false` 时，按给出的 `gaps` 和 `suggestions` 修订计划再评，**最多两轮**；两轮仍不过就接受当前计划往下走，不要空转。

**3. 执行步骤**，把该召回的信息收齐。

## 第三步：给分析——B 式还是 C 式

先判断手上的证据够不够，再决定形态。这一步决定给出的分析有没有价值。

**B 式（默认，证据够）**：列 2-3 条可选路径，每条写清利弊与风险，最后给**一个倾向性建议**——依据用户的历史与处境，不是通用道理。用户要的就是这个倾向；只罗列不表态，等于把活又推回给他。

**C 式（降级）**：证据不足、互相矛盾、或超出你能判断的范围时，**不要硬编一个模糊答案**。把已知事实与各方立场摆清楚，明说"目前信息不足以给倾向性建议"，把判断权交还用户。

这里关键是诚实。编一个"貌似有理"的建议比承认不知道更伤人，因为用户分不出来。而且说清楚缺什么，用户往往当场就能补上——这反而推进了事情。

**搜到的内容是你判断的依据，不是要念给用户听的。** 别把日记原文成段复述——那是他自己写的，他记得；他要的是你从中看出了什么。

**涉及人物时**，结合档案里的特质、喜好与关系变化来说，别停在"要考虑对方感受"这种谁都会说的话。

## 第四步：问要不要记下来

给出分析后，**问用户要不要把这次决策记下来**（比如"要不要把这次决策记下来？"）。

只有用户**明确同意**，才调 `decide_save` 写入。用户拒绝或没回应就不保存，也不要再问第二遍。

**写的时候把这四样写全：**

| 写什么 | 字段 | 注意 |
|---|---|---|
| 决策问题 | `topic` | 用能定位这件事的关键词，不是泛泛的一句话 |
| 最终选择 | `decision` | 结论本身，说清选了什么 |
| 理由与分析 | `reasoning` | **选项和权衡也写进这里**——没有单独的选项字段 |
| 涉及人物 | `people` | 谁参与了、谁受影响 |

日期由工具自动记录，不用你传。

**理由和人物一定要写具体。** 这两样正是将来 `journal_recall` 的搜索词——今天写得越清楚，以后在类似处境里就越搜得到。这和第一步"搜索词要选准"是同一件事的两头：**你现在写下的，就是未来的你能查到的。**

决策写进的是**日记**而不是长期记忆——因为它是"某个时刻发生、有上下文的事件"，不是"永久成立的事实"。
