# 如果让我设计 LICode 的 RAG 记忆召回

> 给面试者的一句话：这篇文档讲的是"给一个真实的个人 AI 助手加上 RAG（检索增强生成）"，实际会踩哪些坑、怎么一个个解决。全程跟着 **背景 → 遇到问题 → 为什么这么选 → 怎么落地 → 又遇到问题 → 再解决** 的循环走，不看代码也能读懂坑在哪。

---

## 一、背景：LICode 和它的记忆

LICode 是跑在终端里的个人 AI 助理。它有个跨会话记忆系统：把用户的偏好、项目背景、纠偏反馈、收藏的资料，一条条存成 markdown 文件（分四类），放在项目目录下。

用户问问题时，助理需要从这些记忆里"回忆"出相关的那几条，放进上下文再回答。这个"回忆"的动作，就叫**记忆召回**。

一句话：**RAG 要干的事 = 从几百上千条记忆里，又快又准地挑出跟当前问题最相关的几条。**

## 二、一开始遇到什么问题：原召回方式不好用

原方案的做法：每次需要记忆时，派一个 LLM 子代理，把"所有记忆的目录"（每条记忆的名称、简介、关键词、第一行）全部喂给它，让它挑出相关的。

实测下来有三个毛病：

1. **误召回高**：测试里"不该召回"的轮次，有 50%–63% 被注入了无关记忆。用户问"docker 怎么入门"，它把"docker 命令备忘"这种只是沾边的也塞进来了。
2. **不稳定**：同一次询问跑两次，结果不一样。
3. **贵**：22 轮对话触发了 64 次 LLM 请求（每次都要带全量目录）。

于是想：能不能让"挑记忆"这一步变得**快、准、便宜、可复现**？

## 三、为什么这么选型：先把方案框架定下来

核心思路一句话：**LLM 只负责"判断要不要用记忆、用哪些"，不负责"从全量里大海捞针"。捞针这一步交给确定的、便宜的检索。**

**1. 接口要稳（先定契约，再谈实现）**

定义一个"检索器"接口：输入问题 + 几个关键词，输出记忆 id 列表。底层用什么都行——关键词匹配、向量相似度、还是以后换更好的——只要接口不变，主模型无感知，测试不用重写。**这是整个设计的地基：可插拔。**

**2. 把文字变成数字来比（embedding）**

记忆和问题都要先转成"向量"（一串数字），谁的数字接近谁就相关。选型关键点：

- **模型选中文强的**（如 BGE 系列）——LICode 的记忆以中文为主，模型的语义能力比"用哪个数据库"重要得多。
- **本地跑，不发第三方**——产品定位是本地优先、注重隐私，把用户记忆发给云端的向量服务与定位冲突。
- **召回时零 LLM 调用**——算相似度是本地数学运算，不花钱、不慢。

**3. 向量存哪：先不选数据库**

记忆量现在几十条、未来几百上千条，每条几百字。这个量级**根本不需要向量数据库服务**（那种为百万级数据设计的重型武器）：

- 起步：向量直接放一个 JSON 文件，查询时全读进内存算相似度，毫秒级。零新增依赖。
- 等真到上千条：迁到一个轻量嵌入式数据库的向量功能（SQLite 带向量扩展），还是不需要单独起服务。

> 反直觉的点：**个人助理的场景，向量库选型几乎不构成瓶颈，真正难的是后面几节讲的"分块"和"同步"。**

## 四、怎么实施：分块、存储、检索

**1. 分块：一条记忆切成几段，每段一个向量**

为什么按"段"切，而不是按固定字数硬切？

因为 LICode 的记忆**天生就是段落式的**，而这不是巧合：记忆是"每次对话沉淀一条独立事实，多次追加"累积出来的，追加的语义就是"补充新段落"；存储层还会按空行做段落去重。也就是说——**段落是记忆生产机制里已经存在的格式**。分块规则直接复用这个现成契约，不发明新格式。

一个附带好处：这样分块，追加新段不会让后面所有段落的边界变动，**只有真正变了的段落才需要重算**（下节详述）。固定字数切分做不到这一点。

**2. 检索流程**

```
问题 → 转向量 → 找最接近的几段 → 归并回记忆 → 交给主模型
同时 → 做关键词匹配，和向量结果合并打分
```

## 五、落下去遇到的第一个坑：语义陷阱（相似 ≠ 相关）

**现象**：向量模型算的是"语义距离"。问"docker 怎么入门"，模型觉得"docker 命令备忘"听起来很像，就召回了——但用户这次不是想问这个。

**为什么躲不掉**：向量相似度衡量"听起来像不像"，分不清"想了解 docker"和"记过 docker 备忘"是不是同一件事。这不是调参能修的，是这类模型的固有能力边界。

**怎么解决**（三层防线）：

1. **加阈值**：相似度太低的不进候选。
2. **混合打分**：关键词精确命中 + 向量语义接近，两边一起算分，别只靠一边。
3. **最关键的：向量只做"初筛"，终审仍留给 LLM**。向量负责从全量里快速捞出一小批候选，最终"注入哪几条"仍由主模型判断。

> 一句话记住这个分工：**检索器负责"找可能相关的"，LLM 负责"确认真的相关的"。检索器永远不当最终裁决者。**

## 六、第二个坑：记忆频繁更新，向量库怎么跟上？

**现象**：用户天天用，记忆一直在变——新增、追加、改写、归档、删除。向量库里的旧向量会过期，甚至残留"已删除内容"的向量，导致以后把过期内容搜出来当真的。

**先补一个底层常识：向量数据库长什么样？** 它其实是一张表，每一行 = 一个唯一编号（id）+ 一串数字（向量）。它有两个能力：一是**按 id 精确增、删、查**——这一点跟普通的键值存储（key-value）一样，你能精确指着一行把它删掉；二是"给一串数字，找出最接近的几行"，这是它独有的看家本领，普通键值存储做不到。**记住第一点"能按 id 精确删"，后面所有同步和删除都建立在这上面**。

**不能每次都全量重算**：上千条重算要几分钟，用户等不起。

**解决思路是三层配合**：

1. **修改时间做初筛**：只有"最近动过"的记忆文件才看，其它跳过。
2. **内容指纹核对**：用一段内容的"指纹"（哈希）判断——如果只是文件被 touch 了一下、内容根本没变，指纹一样，**不重算**。这挡住了"看起来变了其实没变"的假警报。
3. **只重算真变的那条**：变了，就重算这一条记忆变了的几个段落。

**最难的是删除**，也是最容易漏的坑：

- 内容删了一段 → 那段旧向量还赖在表里 → 以后会把已删除的内容搜出来。
- 解法：每段向量的 id 带上"内容指纹"。**内容变了，指纹就变，id 就变。** 新老 id 一对账：消失的删掉、新增的加上、没变的复用——旧内容自动清理干净。
- 整条记忆被归档/删除 → 按记忆 id 一次清空它的所有段落向量。

**兜底**：启动时把"磁盘上现存的记忆"和"向量表里已索引的记忆"对一遍账，有出入就修。运行期万一漏掉的洞，下次启动自动补上。

## 七、第三个坑：用户会问"全局性的问题"，传统 RAG 答不好

**现象**："我最近在忙什么""我和某人的合作是怎么发展的"。这类问题靠"捞几条零散片段"拼不出来，要的是整体视角。

**要不要上 Graph RAG**（把记忆抽成"实体 + 关系"的图，再回答跨片段的全局问题）？

先看清代价：抽图每次都要用 LLM 跑一遍，成本高；而且图是全局的，**一条记忆一变，整张图跟着动**，维护极其痛苦。对"碎片化、频繁更新"的个人记忆，这是灾难。

**实际解法**：先看看你手里已有的结构化信息。LICode 的记忆本来就分四类（用户 / 项目 / 人物档案 / 资料），"谁、哪个项目、什么目标"这类全局骨架**已经以数据结构的形式存在了**——直接按分类聚合就能回答全局问题，零抽取成本、完全确定、还好维护。

> 结论：**别急着上 Graph RAG。** 等记忆真的长成"大量无结构的长文"再说。先把已有分类结构用起来。

## 八、第四个坑：召回效果不理想，怎么排查？

**现象**：上线后才发现，该召回的记忆没召回（漏），或不该召回的混进来了（误）。这是最常被追问的一问，不能凭感觉调，要有套路。

**第一步：先分清是"漏"还是"误"**——两者修法方向相反，别混着调：
- **漏**（召回率低）：该出的记忆没出 → 检索引擎太保守，或索引没建好。
- **误**（准确率低）：无关记忆混进来 → 阈值太低，或撞上语义陷阱。

**第二步：先查"数据对不对"，成本最低**。大多数"效果差"其实死在数据层：
- 记忆入库了吗？向量表数量和磁盘记忆对得上吗？
- 有没有索引过期（改了没重算）、残留孤儿向量？
- 分块有没有丢内容（超长段落被切坏）？
- ——这正是前面"启动对账自愈"的意义：先排除索引是脏的，再谈调参。

**第三步：再查"问题表达"行不行**。如果用户问题是隐指的（"那个项目后来怎么样了"），关键词天然抓不住。这是检索方式的能力边界，不是调参能救的——该让主模型先把问题转成明确的召回意图（LICode 的 memory_recall 就是主模型先产出查询意图和关键词）。

**第四步：分层调检索引擎，每次只动一个旋钮**：
- 阈值：调高更保守（少误，可能漏）；调低召回更多（多误）
- 候选数量：太少漏、太多误
- 混合权重：关键词和向量各占多少
- 重排加分：类型匹配、关键词命中、使用频率

**第五步：都调了还不行，往上游换大件**：
- 换更强的中文向量模型——单次提升最大的改动
- 优化分块（段太长稀释细节？边界切坏了？）
- 给检索结果加一道"复核"：让 LLM 确认候选是不是真相关（"初筛 + 终审"里，终审这环还没用上）

**最后：用评测量化，别凭感觉**。固定一批真实问题（标注好"该召回哪几条"），每次改动跑同一套，对比召回率 / 误召回率。没有数字，"感觉变好了"不可靠。

## 九、剩下的实际坑（简短清单）

| 坑 | 解决 |
|---|---|
| 向量模型国内下载不动 | 模型本地缓存 + 镜像源 + 下载失败时自动退回纯关键词检索（降级不死） |
| CLI 体积膨胀（模型几百 MB） | 向量模型做成可选依赖，默认不装；关掉就纯关键词 |
| 以后换模型、向量维度变了 | 索引文件记下"用的哪个模型、维度多少"，不匹配自动重建 |
| 怎么证明这套比原来好 | 直接在原有评测用例上跑，同一套判定标准对比：召回率 / 误召回率 / 请求次数 |

## 十、给面试者的一句话总结

**RAG 落地，80% 的工作量不在"选向量库、接 embedding API"，而在下面这五件事：**

1. **接口要稳**：检索器可插拔，换实现不影响上层和测试。
2. **分块要贴合数据形态**：记忆是段落式的，就按段落切；分块规则跟着"数据是怎么生产出来的"走。
3. **同步是重头戏**：增量更新 + 内容指纹去重 + 删除自动清理 + 启动自愈——"记忆会变"这件事必须当一等公民设计，不是事后补丁。
4. **向量检索只做初筛，不当终审**：语义陷阱是 embedding 的固有边界，靠阈值、混合检索、LLM 终审来兜。
5. **全局问题别急着上 Graph RAG**：先利用你已有的分类结构，成本是零。
