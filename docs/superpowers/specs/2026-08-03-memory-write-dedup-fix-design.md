# 记忆写入查重指令修复设计

- 日期：2026-08-03
- 状态：已批准（待写实现计划）
- 范围：仅 `packages/core/src/conversation/templates/memory-guide.md` 措辞，零代码改动

## 问题

会话 `1c5ce4cf-f80c-47d0-a19e-ec3abfcbc918` 中，用户说"记住我决定今年12月回趟家"（一条 project 类型的新记忆），模型第一步却 `Read` 了 `.licode/memory/user/favorite-dish-tomato-egg.md`（番茄炒蛋，与"12月回家"无关），读完才正确地 `Write` 创建了 `.licode/memory/project/return-home-dec-2026.md`。

最终写入结果正确，但中间多了一次与主题完全无关的 `Read`。

## 根因

`memory-guide.md` "如何保存"小节的一条指令：

> 创建前先用 Read 检查同主题文件是否存在--更新它，而非新建重复文件

该指令有两个设计缺陷：

1. **用错了工具查重。** "检查同主题文件是否存在"应看**索引**（MEMORY.md 已整份注入上下文，见 `loader.ts:7-17` 的 `memory` 层）。索引每条记忆带一句话 description，扫一眼即知有无同主题。`Read` 只能看单个文件内容，无法回答"是否存在同主题"。指令却写"先用 Read"。

2. **对新主题无合法目标。** "12月回家"在索引里无同主题条目。理想模型应跳过 `Read` 直接 `Write`。但"先用 Read"是祈使句，弱模型倾向于"总得 Read 一个"，于是抓一个显著的旧记忆读。

### 为什么偏偏是番茄炒蛋

无法直接观测模型内部动机，但最可能是**显著性**：上一轮自我介绍时模型刚主动说过"爱吃番茄炒蛋和咖喱牛肉"（会话第 40 行），番茄炒蛋是上下文里最鲜活的那条。当指令逼它"Read 一个同主题文件"又找不到真同主题时，它抓了最显眼的一条。可能叠加 deepseek-chat 把"回家"与"家常菜"做了松散联想，或把它当格式模板读。无论哪种，根因同一条：指令让模型在"没有合法目标"时仍去 Read，模型自己造了一个目标。

## 定性

| 环节 | 结论 | 依据 |
|---|---|---|
| 根因 | 设计问题 | `memory-guide.md:48` 用 Read 做查重 + 对新主题无合法目标，相关性判断全权丢给模型且无护栏 |
| 放大 | 模型问题 | deepseek-chat 指令遵循/相关性推理弱，该跳过 Read 时没跳过 |
| 召回系统 | 不背锅 | 会话里无 `memory_recall` 注入对；`recall.ts:162-191` 的 strict filter 对 write 请求本应返回 `[]`，番茄炒蛋全文非召回注入 |

设计挖坑，模型踩进去。换更强模型踩坑概率降低，但坑仍在--该指令对任何"新主题"场景都天然无正确答案。

## 方案选型

选定 **Approach A2：保留写时查重，修对措辞 + 堵"当模板读"**。

### 备选与取舍

- **A1（最小改写，仅条件化第 48 行）**：把"先用 Read"改成"看索引，有同主题才 Read，无则直接 Write"。直接修缺陷二，但未显式堵"当格式模板 Read"这一动机。
- **A2（最小改写 + 反例，选定）**：A1 基础上再加一条"不要为看格式去 Read 旧记忆"。覆盖本次 bug 的两个可能动机（找同主题找不到 / 看格式）。成本几乎为零。
- **B（服务端查重工具 `memory_save`）**：新增专用工具，服务端决定 update-vs-create，移除模型自主 Read。对弱模型最稳，但改动大（新工具+注册+测试+改指令），且服务端查重也要调 LLM、加延迟。过度设计，留作升级路径。
- **C（移除写时查重，靠 dream）**：删第 48 行，直接 Write，重复交 dream 后台合并（`dream.ts` Orient 阶段找重复主题、consolidate 阶段 update/merge/delete）。最简单，但 24h/5 会话内有重复条目，且 dream 亦为 deepseek-chat 驱动。用户选择保留前端查重，故不取。

选 A2：外科手术级、直击根因、保留既有功能、符合 CLAUDE.md surgical 原则。先验证，不通过再升级 B。

## 具体改动

`packages/core/src/conversation/templates/memory-guide.md`，"如何保存"小节。

**删除**：
> - 创建前先用 Read 检查同主题文件是否存在--更新它，而非新建重复文件

**替换为两条**：
> - 创建前先看索引（已注入上下文）判断有无同主题条目：有则 Read 该文件并更新；无则直接 Write 新文件，不要 Read 任何不相关的旧记忆
> - 需要文件格式时参照上方 frontmatter 模板，不要为看格式去 Read 旧记忆

其余行不动。不触碰第 56 行（"索引已注入上下文；需要正文时用 Read 读取对应文件"）--该行正确，新 bullet 已与之呼应。

## 成功标准

- **新主题场景**：说"记住我决定今年12月回趟家"（索引无同主题）-> 第一个工具调用是 `Write`，**不**出现对任何旧记忆的 `Read`。
- **同主题场景**：说"记住我其实更爱吃糖醋排骨"（索引有 `favorite-dish-tomato-egg`）-> 先 `Read` 该文件再 `Write` 更新，不新建。
- 写入的记忆 frontmatter 与正文仍符合现有规范（type/slug/dates 正确）。

## 验证计划

1. **手动回放（主）**：CLI 起会话，依次跑上述新主题与同主题场景，观察工具调用序列。
2. **可选集成测试**：temperature=0 调 deepseek-chat，注入改后 system prompt + 新主题用户消息，断言首个工具调用是 `Write` 而非 `Read`。模型非确定性，属锦上添花，不作为硬门槛。

## 残余风险与升级路径

deepseek-chat 仍可能偶发误读新措辞。若手动回放仍复现无关 Read，升级到 Approach B（`memory_save` 服务端查重工具，移除模型自主 Read 的 agency）。先 A2 验证，避免一上来过度设计。

- 不加新工具、不改代码逻辑。
