# 记忆召回架构对比：新（工具召回）vs 旧（side-query 注入）

> 本文档只记录两个架构的**事实**（含测量结果与代码层面的可证属性），不包含"该保留/修复哪个版本"的任何建议。
> 每条事实标注来源：`[实测]` = A/B 评测测得；`[设计]` = 从代码/架构层面可验证的事实。
> 完整评测过程与数据见 `packages/core/scripts/eval-recall/A-B-test-v1.md`。
> **2026-08-20 更新**：下表新架构的 B 组数字为**优化前**的测量。提示词优化（工具描述收紧 + 子代理语义陷阱自检 + 默认弃权置顶 + maxResults 5→3 + 惯性抑制 + 原样传用户问题）后，新版单轮 B 组误召回（注入）降为 **0%**、误触发 38–50%、精度 93%，A/D 组不变，详见 A-B-test-v1.md §10。

## 3. 旧架构（side-query 注入）优缺点

### 优点

- `[实测]` 误召回率低：单轮 B 组 13%，多轮不该召回轮误召回仅 12.5%。（旧版触发即注入，误触发率同值）
- `[实测]` 完全确定性：多次运行逐条结果一致，跨 key 一致。
- `[实测]` 请求数少：多轮 22 轮共 44 次（每轮恰好 1 次主对话 + 1 次 side-query）。
- `[实测]` 防幻觉弃权合格：D 组联想 0%。
- `[设计]` 召回决策链路单一：每轮固定 side-query 选摘一次，无子代理多步，排查直观。
- `[设计]` side-query prompt 有强默认空（"不确定相关的不放入 add"），倾向保守。

### 缺点

- `[实测]` 召回率较低：单轮 A 组 91%，多轮 92.9%；漏 a4（"这周哪几天**晚上**有空锻炼"只召回新晨练**早上**安排，读不懂时间约束）、多轮项目会话 t2 漏 q3-launch。
- `[实测]` 缓存命中率低：多轮主对话缓存 89.4%，总缓存 84.2%；非缓存计费 input 17,371（约为新版的 2.4 倍）。
- `[实测]` 时序/时间约束理解弱：偏好 recency（取最新记忆）但无法结合查询中的时间条件做区分。
- `[设计]` 每轮必跑 side-query：即使当前无需召回也固定消耗一次 LLM 调用。
- `[设计]` 注入内容每轮进入主对话历史，历史前缀随注入变化，拖累跨轮缓存命中。
- `[设计]` 主模型无召回决策权：不能按需自主召回，只能接收 side-query 注入结果。

## 4. 新架构（memory_recall 工具）优缺点

### 优点

- `[实测]` 召回率高：单轮 A 组 100%，多轮累积召回 100%；知识更新/多跳/隐指/关系/个人细节类用例全中。
- `[实测]` 缓存命中率高：多轮主对话缓存 96.8%，总缓存 95.3%；非缓存计费 input 7,109（较旧版低约 59%）。
- `[实测]` 防幻觉弃权合格：D 组联想 0%。
- `[设计]` 主模型按需自主决定召回：正常轮次不调用即零召回开销，调用才把记忆正文引入上下文。
- `[设计]` system prompt 为静态存在提示层，前缀跨轮稳定，利于缓存命中。
- `[设计]` 子代理可多步调用 `read_memory` 读正文复核弱匹配，非纯靠索引关键词。

### 缺点

- `[实测]` 误触发率高：单轮 B 组 50–63%（含空触发）；按"实际注入无关记忆"计误召回率 25–37.5%；多轮不该召回轮误触发 100%（工具惯性），其中误召回 3/8。
- `[实测]` 语义陷阱失效：b5（健身 App 数据库）注入团队分工/编辑器/健身；b7（Neovim 入门）注入 neovim-workflow；b8（docker）注入 docker-cheatsheet 等无关记忆。
- `[实测]` 非确定性：是否调用工具、子代理选中哪些记忆，跨运行有抖动。
- `[实测]` 请求数多：多轮 22 轮共 64 次（主对话 + 子代理多步），高于旧版 44 次。
- `[设计]` 两段式架构：主模型触发 + 子代理选择，两个环节各自可能误判，故障排查链路更长。
- `[设计]` 子代理 maxSteps=4 限制下，步数不足时可能未读正文就凭索引关键词初筛选中，落入关键词近似匹配陷阱。
- `[设计]` 主模型工具调用判据依赖提示词描述（"可能受益于…时调用"），无强约束时调用偏宽。
